# نظام إدارة المهام والمشاريع (المشروع التكاملي)

**مادة:** تحليل وتصميم الخوارزميات — الفصل الدراسي الصيفي 2026
**التقنيات:** Java (خادم HTTP + REST API + الخوارزميات) وواجهة ويب HTML/CSS/JS

## الفكرة

نظام مبسط لإدارة المهام (لوحة كانبان) يطبق **مفهومين خوارزميين فقط** لحل مشاكل إدارية حقيقية:

1. **خوارزميات الترتيب بالمقارنة (Comparison Sorting)** — Quick Sort وMerge Sort
2. **تقنية فرّق تسد (Divide and Conquer)** — حساب الجهد الكلي للمشروع

## طريقة التشغيل

1. تأكد من تثبيت **JDK** على الجهاز (javac وjava).
2. شغّل الملف `run.bat` (نقرة مزدوجة).
3. افتح المتصفح على: <http://localhost:8080>

أو يدوياً:

```bat
javac -encoding UTF-8 -d out src\app\*.java
java -cp out app.Main
```

## المتطلبات الخوارزمية

### 1) خوارزميات الترتيب بالمقارنة — `src/app/QuickSort.java` و`src/app/MergeSort.java`

**المشكلة:** المدير يحتاج رؤية المهام مرتبة حسب الأولوية (الأعلى أولاً) أو حسب التاريخ المتبقي (الأقرب أولاً).

**التنفيذ:** تنفيذ يدوي كامل لخوارزميتين مختلفين **بدون استخدام الدالة الجاهزة sort()**. عند الضغط على زر "ترتيب" يتم عرض القائمة مرتبة، مع **زمن التنفيذ بالمللي ثانية** وعدد المقارنات لكل خوارزمية على الشاشة لمقارنة أدائهما.

**تحليل التعقيد:**

| الخوارزمية | أفضل حالة | أوسط حالة | أسوأ حالة |
|---|---|---|---|
| Quick Sort | O(n log n) | O(n log n) | **O(n²)** |
| Merge Sort | O(n log n) | O(n log n) | O(n log n) |

- **Quick Sort O(n log n):** عند القسمة المتوازنة تكون شجرة الاستدعاءات بعمق log n، وفي كل مستوى تُقارن n عناصر، فيكون المجموع n·log n.
- **Quick Sort O(n²) (أسوأ حالة):** إذا كان المحور (Pivot) دائماً أصغر أو أكبر عنصر — مثلاً قائمة مرتبة مسبقاً مع اختيار آخر عنصر كمحور — تصبح القسمة غير متوازنة (جزء بحجم 0 وجزء بحجم n-1) فيصبح عمق الشجرة n والمجموع n².
- **لماذا يتفوق Merge Sort في أسوأ الحالات؟** لأنه يقسم دائماً نصفين متساويين بغض النظر عن البيانات، فيضمن عمق log n وأداء O(n log n) دائماً، بينما يعتمد أداء Quick Sort على اختيار المحور.
- في المقابل Quick Sort أفضل عملياً غالباً لأن القسمة (in-place) لا تحتاج ذاكرة إضافية وثوابت مخفية أصغر.

### 2) فرّق تسد (Divide and Conquer) — `src/app/EffortCalculator.java`

**المشكلة:** حساب إجمالي عدد الساعات/الجهد المطلوب للمشروع الكامل بناءً على المهام الفرعية المتداخلة (الشجرة الهرمية).

**التنفيذ:** دالة **Recursive** تستقبل المهمة الجذر (المشروع)، تقسمها إلى مهام رئيسية، ثم إلى مهام فرعية، تحسب مجموع الأوقات المتوقعة لكل فرع باستدعاء ذاتي، ثم تدمج (تجمع) النتائج لإظهار إجمالي وقت المشروع:

```
effort(task) = task.hours + Σ effort(children)
```

لم نستخدم حلقة for لجمع الأوقات مباشرة، بل استدعاء ذاتي يبني **شجرة استدعاءات (Call Tree)** — كل مستوى في الشجرة يمثل إطاراً على **مكدس الاستدعاءات (Call Stack)**، ويظهر جدول الاستدعاءات كاملاً في صفحة "فرّق تسد — الجهد".

**التحليل:** التعقيد **O(n)** حيث n عدد المهام، لأن كل عقدة في الشجرة تُزار **مرة واحدة فقط** (زيارة واحدة تعني حساب ساعاتها وجمع جهود أبنائها). الفضاء O(h) على المكدس حيث h عمق الشجرة.

```
│   ├── MergeSort.java       ← خوارزمية الترتيب بالدمج (يدوي)
│   ├── EffortCalculator.java← فرّق تسد: حساب الجهد الكلي
│   └── Json.java            ← أدوات JSON مساعدة
└── web/
    ├── index.html           ← واجهة عربية RTL
    ├── style.css            ← التصميم
    └── app.js               ← منطق الواجهة
```
